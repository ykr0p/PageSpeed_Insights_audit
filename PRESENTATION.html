Метрики и стандарты

Что такое Core Web Vitals и почему они влияют на всё

Google использует Core Web Vitals как прямой фактор ранжирования в поисковой выдаче и критерий качества пользовательского опыта (UX).

LCP (Largest Contentful Paint)

Время отрисовки самого крупного видимого элемента страницы (главный текст, баннер, карточка).

Норма: ≤ 2.5 секунды
CLS (Cumulative Layout Shift)

Суммарный сдвиг разметки при дозагрузке шрифтов, баннеров, асинхронных блоков без фиксированной высоты.

Норма: ≤ 0.1000
TBT / INP (Интерактивность)

Время блокировки главного потока процессора долгими скриптами JS до отклика на клик пользователя.

Норма: TBT ≤ 200 ms | INP ≤ 200 ms
Дополнительные фундаментальные метрики:
TTFB (Time to First Byte): Ответ сервера и старт ответа (норма ≤ 800 ms).
FCP (First Contentful Paint): Первая видимая отрисовка пикселей (норма ≤ 1.8 с).
Speed Index: Скорость визуального наполнения контентом.
Методология аудита

Cold (Холодный) vs Hot (Горячий) запуск: В чем разница?

Замерять производительность только в одном режиме — классическая ошибка. Реальные пользователи делятся на две принципиально разные группы:

❄️ Холодный запуск (Cold Run)

Новый посетитель
  • Кэш браузера полностью пуст (HTTP 200 на все файлы).
  • Выполняется полный DNS-lookup, TLS/TCP handshake.
  • Скачиваются все CSS-стили, шрифты WOFF2, JS-бандлы и картинки.
  • Пул соединений базы данных и серверный кэш могут быть «холодными».
  • Как замеряем: принудительный сброс кэша браузера через CDP Network.clearBrowserCache или cache-buster параметры в PageSpeed API.

🔥 Горячий запуск (Hot Run)

Повторный визит
  • Статические ресурсы загружаются мгновенно из дискового/памятного кэша браузера (from disk cache, 304 Not Modified).
  • Keep-Alive соединение уже открыто.
  • Прогрет пул соединений Prisma / PostgreSQL.
  • Что показывает: чистую производительность генерации данных, эффективность клиентского кэша и гидратации React.
💡 Инсайт Workdo: В исходном коде горячий режим иногда был медленнее холодного из-за повторных вызовов rate-limiter Upstash и очередей запросов. Исправление серверной логики сделало горячий запуск в 2 раза быстрее холодного!

Глубокий анализ проблем

Капкан №1: Внешний Rate Limiter в Server-Side Rendering

Казалось, что тормозит база данных или React. Настоящий виновник — синхронные проверки лимитов через внешний REST API Upstash Redis во время генерации HTML.

❌ Как было устроено (4.3 секунды оверхеда):

1. На странице дашборда page.tsx вызывалось 5 серверных экшенов.
2. Каждый экшен вызывал assertUserActionRateLimit.
3. Redis работал по внешнему REST API (~215 ms задержки).
4. Проверялись 2 ключа последовательно, и каждый делал TTL + INCR + EXPIRE последовательно! 

5 экшенов × 4 сетевых запроса × 215 ms = 4 300 ms задержки!

✔ Архитектурное решение (Split Rate Limiter):

1. Разделение на чтение и запись: Для всех SSR-чтений внедрен mode: "read". Во время рендеринга страницы обращения к внешнему Upstash полностью исключены (0 ms оверхеда).
2. Защита мутаций: Все 226 мутаций (Write) защищены строгим лимитом через атомарный Lua-скрипт (1 вызов вместо 3).
3. Anti-Spoofing: Заголовок x-action-rpc генерируется только внутренним reverse proxy.

Итог: SSR оверхед снижен с 4300 ms до 0 ms!
Глубокий анализ проблем

Капкан №2: Водопад N+1 в расчете зарплат (16.8 секунд)

Страница /security/salary висела более 16 секунд из-за последовательного расчета каждого сотрудника в цикле.

❌ БЫЛО: 100 последовательных запросов к БД

// page.tsx - последовательный перебор
for (let i = 0; i < guards.length; i++) {
  // На каждого охранника открывалась транзакция,
  // выполнялся SELECT смен, расчет надбавок и штрафов
  await calculateMonthlySalaryAction(guards[i].id);
}
// ИТОГ: 16 788 ms время рендера страницы!

✔ СТАЛО: Пакетный SARGable SQL-запрос

// 1 пакетный запрос с диапазоном дат
export async function getMonthlySalariesBatchAction(period) {
  const existing = await salaryRepo.findManyByPeriod(period);
  const timeRecords = await timeRecordRepo.findRange({
    where: {
      date: { gte: period.start, lt: period.end } // SARGable индекс
    }
  });
  return computeBatch(guards, timeRecords, existing);
}
// ИТОГ: 869 ms (в 19 раз быстрее!)
💡 Принцип: Никогда не делайте await db.query() внутри цикла в серверных компонентах. Группируйте идентификаторы в WHERE id IN (...) или пакетные интервалы дат.
Клиентская оптимизация

Клиентские капканы: Каскадные таймеры и opacity: 0

Ошибки в использовании библиотек анимации (Framer Motion) блокировали процессор на 3.5 секунды и ломали LCP.

1. Каскадные таймеры (TBT 3516 ms)

В списках сотрудников каждая строка рендерилась как: <motion.tr transition={{ delay: index * 0.05 }} />. На 100 строках браузер создавал 100 JS-таймеров одновременно, полностью замораживая UI.

Решение:
Убран Framer Motion с элементов списков таблицы, TBT упал с 1042 ms до ~0 ms!
2. initial={{ opacity: 0 }} на LCP (Задержка 1-2 с)

Заголовки Hero-секции <h1> были невидимы до окончания гидратации JS и завершения CSS-перехода.

Решение:
Для элементов выше сгиба экрана (Above the Fold) убран начальный нулевой opacity. Заголовок виден мгновенно в сыром SSR HTML!

3. Динамическая загрузка тяжелых библиотек (Recharts)

В модуле финансов библиотека графиков recharts весила ~200 KB и блокировала рендер. Вынесена в next/dynamic(() => import(...), { ssr: false }) с отображением легковесного скелетона во время загрузки.

Борьба с Layout Shift: Как достичь CLS = 0.0000

Сдвиги разметки (CLS) раздражают пользователей и пессимизируются поисковиками. В Workdo было решено 2 ключевых источника сдвигов:

1. Кириллический сабсет шрифта Inter

Шрифт Inter был подключен только с subsets: ["latin"]. Русский текст рендерился системным Arial, а затем принудительно перерисовывался браузером, сдвигая строки. 

// layout.tsx
const inter = Inter({
  subsets: ["latin", "cyrillic"], // Добавлена кириллица
  display: "swap"
});

2. Сметы: Резервирование высоты калькулятора

На странице /security/estimates/[id]/edit блок расчета итогов сметы вызывал CLS 0.2152 при загрузке данных. 

// Зафиксирована минимальная высота и синхронизирован скелетон
<div className="min-h-[108px] rounded-lg border p-4">
  {loading ? <SkeletonTotals /> : <TotalsSummary />}
</div>
// ИТОГ: CLS снижен с 0.2152 до 0.0000!
Системный подход

9 Блоков Оптимизации: Хроника трансформации

Блок 1–2: SSR & Parallel

Promise.allSettled в page.tsx. Устранение дублирующего шрифта Inter из globals.css. Снятие opacity: 0 с шапки.

Блок 3: Lua в Redis

Сворачивание 3 сетевых вызовов Upstash в 1 атомарный EVAL скрипт. Параллельный Promise.all для ключей.

Блок 4–5: Split Rate Limiter

100% разделение чтения (0ms на SSR) и мутаций (60/мин) во всех 3 вертикалях: Security, Beauty, Yacht.

Блок 6: Пакетный SQL & Preload

Ликвидация N+1 в зарплатах (16.8с → 869ms). Прелоад форм редактирования на сервере без спиннеров.

Блок 7: Переход на Pure SSG

35 публичных страниц переведены в force-static. Анимации фона перенесены на GPU Compositor.

Блок 8–9: Фиксация CLS

Синхронизация скелетонов и фиксация min-height в сметах. Полный аудит 83 страниц: 0 ошибок.

Руководство к действию

Золотой чеклист оптимизации любого сайта

1. Backend & Server Components (SSR)
  • Параллельте независимые запросы данных через Promise.allSettled.
  • Никаких внешних HTTP-обращений (rate-limiter, аналитика) во время рендеринга страницы.
  • Избавляйтесь от N+1 через пакетные SQL-запросы с WHERE IN (...).
  • Публичные страницы переводите в Static Site Generation (force-static).
2. Frontend & Клиентский код
  • Снимайте opacity: 0 с элементов первого экрана выше сгиба (LCP).
  • Не используйте каскадные таймеры (delay: i * 0.05) на строках списков.
  • Выносите тяжелые графики и редакторы в динамические импорты (dynamic()).
  • Резервируйте min-height для предотвращения сдвигов (CLS = 0).

Как запустить созданный PageSpeed Toolkit

Созданный софт в папке F:\Download\TPO\metrics готов к запуску прямо сейчас без сложной настройки:

1. Быстрый аудит любого сайта через терминал: 
# Аудит любого сайта (Cold + Hot, Desktop + Mobile)
node bin/psi-audit.mjs --url https://vash-sait.ru

# Только мобильный аудит
node bin/psi-audit.mjs --url https://vash-sait.ru --device mobile

# Пакетный аудит нескольких страниц из config.json
node bin/psi-audit.mjs --config config.json --open
2. Замер серверного SSR-стриминга (TTFB): 
node bin/ssr-check.mjs https://vash-sait.ru
3. Что генерирует утилита:

* Консольную цветную сводку и таблицу сравнения Cold vs Hot.
* Подробный отчет Markdown (reports/audit_...md).
* Красивый интерактивный HTML-дашборд с круговыми диаграммами (reports/latest-report.html).
