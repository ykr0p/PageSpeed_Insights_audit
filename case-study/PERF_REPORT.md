## Блок 1: быстрый perf (2026-09-26)

Замерялись только страницы, которых коснулись правки: `/register` (auth-layout +
шрифты) и `/security` (дашборд). Условия те же: production build, desktop
1440x900, `throttlingMethod=provided`, hot-режим.

### Результат

| Страница | Hot LCP было | Hot LCP стало | Perf было | Perf стало | CLS |
|---|---|---|---|---|---|
| `/register` | 1841 ms | **739 ms** (−60%) | 89 | **99** | 0.0000 |
| `/security` | 3466 ms | **935 ms** (−73%) | 75.5 | **99** | 0.0000 |

Разброс по прогонам (не медиана, а все замеры):

| Страница | LCP прогоны | Perf прогоны |
|---|---|---|
| `/register` | 1195, 470, 739 | 94, 100, 99 |
| `/security` | 1188, 775, 935 | 97, 100, 99 |

`/register` идёт с **LCP = FCP** (481=481, 616=616, 771=771) — LCP-текст рисуется
с первой отрисовки, сдвигаться нечему.

### Реальная причина тормозов (не та, что предполагалось)

Исходная гипотеза была про шрифты и `opacity: 0` в framer-motion. Замеры её не
подтвердили — и нашли настоящую причину.

**1. `/security`: последовательные запросы в SSR.** `page.tsx` выполнял пять
независимых чтений строго последовательно, каждое добавляло свою задержку к
ответу. Замер потокового ответа (JS отключён, чтобы исключить клиент):

| | responseStart (заголовки) | responseEnd (HTML целиком) |
|---|---|---|
| было | 78 ms | **4040 ms** |
| стало | 135 ms | **895 ms** |

После перевода на `Promise.allSettled` (с сохранением per-query обработки
ошибок) — **−3.1 с** к времени рендера.

**2. Шрифт не содержал кириллицы.** `Inter` был подключён как
`subsets: ["latin"]`, при этом весь интерфейс на русском → браузер подставлял
системный fallback и перерисовывал текст. Добавлен `cyrillic`.

**3. Двойной Inter устранён.** В `globals.css` был `@import` Google Fonts, в
`layout.tsx` — `next/font`. Рекомендация из базовой линии выполнена: `@import`
удалён, остался один `next/font`. Мёртвый `Geist` (ноль ссылок в `src`) убран.

**4. `opacity: 0` у LCP-элементов снят** в auth-layout и в 5 крупных блоках
дашборда (карточки статистики, виджет инцидентов, напоминание об оплате, быстрые
действия, списки смен/инцидентов). Анимации появления на этих блоках убраны
полностью — это осознанная плата за LCP.

### Не подтвердилось

- **CLS-регрессия на `/register`.** Первый прогон показал `0.0562` (было `0.0000`),
  и в отчёт попала как «побочный эффект». Не воспроизвелась: 7 замеров подряд
  (тёплый профиль, чистый профиль, отдельный пробник) дали `0.0000`. Гипотеза
  «метрики шрифта при `font-display: swap`» оказалась неверной — next/font уже
  генерирует метрически-подогнанный fallback сам:
  `@font-face{font-family:Inter Fallback;src:local(Arial);ascent-override:90.44%;descent-override:22.52%;line-gap-override:0.0%;size-adjust:107.12%}`.
  Ручной `size-adjust` не добавлялся — он был бы дублированием.
- **Анимации как причина медленного `/security`** — не подтвердились, LCP
  определялся временем серверного рендера, а не гидратацией.

### Проверено и не является проблемой

- **Пул соединений.** Пять параллельных чтений на `/security` против общего пула
  `src/lib/db/pool.ts` (`max = DB_POOL_MAX ?? 20`) — это 25% ёмкости, и только на
  время запросов. Истощения пула не будет; при росте нагрузки менять нужно сам
  `Promise.allSettled`, а не увеличивать пул.
- **`fcn`/CPU**: TBT и SI низкие во всех замерах, главные потери были в LCP/SSR,
  а не в исполнении JS.

### Известный остаточный риск

После `Inter Fallback` (= `local(Arial)`) цепочка шрифтов продолжается на
`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, 'Helvetica Neue', Arial`
— эти шрифты метрически **не** скорректированы. На машине без Arial (Linux,
Android) метрики поедут и возможен возврат CLS. Лечится заменой цепочки на
кросс-платформенный fallback с overrides.

### Что не перезамерено

80 страниц из 83. Правки шрифта затрагивают весь сайт, поэтому таблица ниже
может быть неточной для всех страниц, а не только для трёх. Полный перезамер —
`npm run perf:audit` (около 10 минут).

### Результат

Замеры на **отдельном production-сервере** (`:3310`, чтобы не трогать

после блока 3 (rate limiter) → **508 ms**. Первый прогон после старта сервера
всегда холодный и не учитывается.

### Изменения

- `page.tsx`: пять чтений (`Shift`, `Employee`, `Post`, `Brigade`, `Object`)
  переведены с последовательных `try/await` на `Promise.allSettled` с сохранением
  per-query логирования ошибок и fallback-значений.
- `shifts-client.tsx`: у `motion.div` шапки убран `opacity: 0` (LCP-заголовок
  ждал гидрацию и окончание анимации). Анимация `y: -20 → 0` оставлена —
  она transform-only и на LCP не влияет.
- `scripts/perf-audit/routes.mts`: адрес замера перенесён в `PERF_BASE_URL`.

Раскладка шапки не менялась: `flex-col md:flex-row md:justify-between` сохранён,
диф относительно HEAD — только снятая анимация прозрачности.

### Откатанный эксперимент: «LCP = FCP»

Промежуточная версия выносила `<h1>` и описание в `page.tsx`, а данные — в
async-компонент под `<Suspense>` со `SkeletonTable`. Это давало
**LCP = FCP (203 / 277 ms, Perf 99–100)**, потому что заголовок рисовался с
первой отрисовки, не дожидаясь данных.

Такая версия **не была принята**: заголовок и кнопка «Добавить смену» оказались
в разных рядах, кнопка уехала вправо-вниз и сломала раскладку страницы. Правка
откачена, шапка возвращена в `shifts-client.tsx` целиком.

Причина — не «неправильный CSS», а архитектурная: кнопка открывает `ShiftForm`,
а форма требует `guards`/`posts`, то есть те же данные. Чтобы заголовок и кнопка
оказались в одном ряду **и** заголовок не ждал данных, форму смены нужно вынести
из календаря в отдельную стримируемую часть. Это рефакторинг с риском для
создания смены, поэтому он не выполнялся.

Итог: LCP упирается в самый медленный запрос (а не в отрисовку оболочки) —
843 ms вместо 3860 ms. Дальнейшее сокращение возможно только вместе с этим
рефакторингом.

### Проверка данных

`shiftDots = 0` в календаре — корректное состояние, а не регрессия: у тенанта
`business 27` все 3 смены датированы 2026-06-12 … 2026-08-15, в сентябре 2026 их
нет (`select count(*) from "Shift" where "startTime" between ...` = 0).

Данные через параллельные чтения доходят: в селекте сотрудников 6 опций
(`getEmployeesAction` → `Promise.allSettled` → `ShiftsClient`).

## Блок 3: настоящая причина — rate limiter в SSR (2026-09-26)

Блоки 1 и 2 чинили страницы. Блок 3 нашёл причину, которая делала **все**
страницы медленными, независимо от того, сколько запросов они делают.

### Как нашли

Профилирование `/security/shifts` с замером каждого запроса отдельно дало
неожиданный результат: пять «разных» запросов укладывались в одинаковые
600–900 ms с разбросом 23 ms.

```
posts    585ms      brigades 602ms
guards   606ms      objects  607ms
shift    608ms  →  all settled 609ms
```

Одинаковая длительность у пяти разных запросов означала не «медленный SQL»,
а общий дорогой пролог. Разбор `requireTenant()` его вскрыл:

| Этап | Время |
|---|---|
| `auth()` | 90 ms |
| `resolveTenantInternal` (было) | ~600 ms |
| **`assertUserActionRateLimit`** | **867 ms** |

### Что там происходит

`getRedis()` — это **Upstash Redis поверх REST** (`src/lib/redis/index.ts`),
то есть каждый лимит — HTTP-запрос во внешнюю сеть, ~215 ms на обращение, а не
локальный сокет. Дальше:

- `assertUserActionRateLimit` проверял **два** ключа (user-wide и per-tenant)
  **последовательно**;
- каждый `checkRateLimit` делал `TTL` + `INCR` (а на первом попадании ещё
  `EXPIRE`) — тоже последовательно.

Итого **4 строго последовательных** обращения к Upstash на один action.
Так как `page.tsx` читает данные через пять `"use server"`-экшенов, один рендер
страницы — это 20 сетевых вызовов, 4 из которых стоят на критическом пути.

Это полностью объясняет исходные 4040 ms `/security`: 5 actions × 4 хопа ×
~215 ms ≈ 4300 ms. Сходится с измерением.

### Правки

| | Было | Стало |
|---|---|---|
| **A** — два ключа лимита | последовательно | `Promise.all`, оба ключа всегда инкрементятся |
| **B** — `TTL`+`INCR`+`EXPIRE` | 3 REST-вызова | 1 вызов (`EVAL`, Lua-скрипт) |

Итог: 4 последовательных хопа → **1**. LCP `843 → 508 ms`.

`pipeline` вместо Lua не годится: конвейер выполнил бы `INCR` до того, как
известно про блокировку, а документированный инвариант требует не инкрементить
счётчик при активном блоке. Ветвление обязано произойти на стороне Redis.

### Проверка лимитера (обязательна, а не опциональна)

Лимитер **fail-open**: при ошибке он молча разрешает всё. Юнит-тесты работают на
in-memory лимитере и Lua-ошибку не поймали бы. Поэтому проверено напрямую против
реального Upstash:

```
OK   счётчик растёт 1,2,3
OK   блокировка срабатывает (на 6-м вызове при лимите 5)
OK   заблокированный остаётся заблокированным (retryAfter 600 → 599)
OK   у заблокированного count = 0   ← инвариант сохранён
OK   другой identifier не затронут
```

### Побочно исправлено: 6 трейсов на один запрос

`traceTenantResolve` был **уже** обёрнут в `cache()`, и комментарий обещал одну
строку лога на запрос. Но `cache()` дедуплицирует по аргументам, а `entry`
собирался заново при каждом вызове (новый `ts`, новый `resolveMs`) — ключ всегда
отличался. На рендер `/security/shifts` приходилось 6 идентичных записей с шагом
3 ms. Теперь состояние «уже записал» живёт в объекте, который `cache()` возвращает
один на запрос.

Также `resolveFromMemberships` обёрнут в `cache()` по `userId`: membership-запрос
в Prisma выполнялся 6 раз вместо одного, `resolve` упал с ~600 ms до 4–32 ms.
Rate limiter при этом намеренно **не** схлопнут — это choke point безопасности.

## Блок 4: Rate Limiter Split, устранение N+1 и оптимизация Security (2026-09-27)

Этот блок устранил ключевые архитектурные узкие места, выявленные в ходе глубокого аудита вертикали Security: сетевой оверхед Upstash при серверном рендере, N+1 водопад в расчёте зарплат, сканы сотен тысяч строк в аудит-логе и последовательные ожидания в бригадах и сотрудниках.

### 1. Архитектурные изменения

1. **Разделение Rate Limiter (Read vs Write) с защитой от спуфинга (`x-action-rpc`):**
   - **SSR-чтения:** Все чтения переведены на режим `mode: "read"` (`requireTenantQuery`, `requireSecurityTenantQuery`). Если запрос выполняется в контексте серверного рендеринга страницы (отсутствует доверенный заголовок `x-action-rpc`), обращение к внешнему Upstash Redis **не выполняется вовсе** (0 ms сетевого оверхеда).
   - **Клиентские RPC-чтения:** Ограничены мягким лимитом 300 запросов/мин и кэшируются через единый ключ в рамках одного HTTP-запроса.
   - **Мутации (Write):** По умолчанию действует строгий режим `mode: "write"` (Fail-Closed). Все 226 мутаций вертикалей защищены лимитом 60 запросов/мин с обязательной проверкой в Upstash.
   - **Безопасность (Anti-Spoofing):** Заголовок `x-action-rpc` формируется исключительно внутренним reverse proxy (`proxy.ts`) и принудительно вырезается из входящих внешних запросов клиента, исключая возможность обхода мутационных лимитов.

2. **Ликвидация N+1 в зарплатах (`/security/salary`):**
   - **Было:** Цикл `for (let i = 0; i < guards.length; i++) await calculateMonthlySalaryAction(guards[i].id)` последовательно запускал 100 транзакций и запросов к БД на рендере страницы $\rightarrow$ **16 788 ms**.
   - **Стало:** Создан пакетный метод `getMonthlySalariesBatchAction` с предзагрузкой существующих зарплат (`findManyByPeriod`) и пакетным SARGable-диапазоном дат в `TimeRecordRepository` (`WHERE date >= :start AND date < :end`).
   - **Результат:** Время рендера страницы упало в 19 раз: с 16.8 с до **869–990 ms**!

3. **Оптимизация журнала аудита (`/security/audit-log`):**
   - **Было:** Загрузка 120 000 строк в память через `getAll({ limit: 10000 })` и `findAll({ limit: 100000 })`, N+1 резолвинг имен сущностей в БД на каждую строку, а также сканирование 1000 записей сотрудников в `getAuditors()` $\rightarrow$ **1 972 ms**.
   - **Стало:**
     - Переход на точечные SQL `DISTINCT` в `AuditLogRepository`.
     - Функция `extractEntityNameFromDetails`: извлечение имени сущности напрямую из JSON `details` в памяти за 0 мс (снимает 80%+ точечных SQL-запросов к БД).
     - Точечный метод `findByUserIds([...seenIds])` для аудиторов (вместо скана 1000 строк).
     - Мемоизация `resolveScope` через React `cache()`.
   - **Результат:** Время полного SSR-рендера упало ниже 1 секунды: с 1 972 ms до **756–954 ms**, а LCP в Lighthouse сократился в 3 раза (с 5895 ms до **1954 ms**).

4. **Параллелизация страниц бригад и сотрудников:**
   - **`/security/brigades`:** 6 последовательных вторичных запросов (`countByBrigade`, `getEmployeeIdsWithBrigade`, `getObjectNamesByIds`, `getLeaderNamesByIds`, `getLastShiftByBrigade`, `historyBrigadeIds`) объединены в `Promise.all`. Вызовы на странице переведены на `Promise.allSettled`.
     *Результат:* Total время упало с 1 319 ms до **625 ms** (в 2.1× быстрее), Lighthouse LCP сократился с 3529 ms до **1253 ms** (Perf вырос с 78 до **90**).
   - **`/security/employees`:** 4 экшена страницы (`getEmployeesCountsAction`, `getEmployeesAction`, `getAllPositionsAction`, `getBrigadesListAction`) объединены в `Promise.allSettled`.
     *Результат:* Total время упало с 1 327 ms до **788–874 ms**, Lighthouse LCP снизился с 5553 ms до **2242 ms**.

## Как перезамерять

```bash
# быстрая проверка серверного рендера, ~8 с, без браузера и без сборки
npm run perf:ssr

# полный аудит 83 страниц (нужен запущенный prod-сервер)
npm run perf:audit        # hot, 3 прогона  -> .perf/hot.jsonl
npm run perf:audit:cold   # cold, 1 прогон -> .perf/cold.jsonl

# точечно по конкретным страницам
npm run perf:audit -- --routes security,auth/register --repeats 1

# атрибуция layout-shift к конкретным DOM-узлам
npx tsx scripts/perf-audit/cls-probe.mts          # CLS_ROUTE=/security
```

`perf:ssr` меряет разницу между появлением заголовков и завершением HTML — именно
она ловит последовательные запросы в SSR (было 4040 ms, стало 895 ms). Порог по
умолчанию 2500 ms, exit code != 0 при превышении, поэтому подходит для CI.
Полный цикл before/after — около 10 минут, из них ~3 мин на `next build`;
`perf:ssr` от сборки не зависит.
