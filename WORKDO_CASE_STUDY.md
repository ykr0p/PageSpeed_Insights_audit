# Кейс Workdo: Как вывести 83 страницы SaaS-системы из красной зоны в 100% зелёную зону Core Web Vitals

> **Реальный кейс масштабной оптимизации мультиарендной B2B SaaS платформы (Workdo)**  
> **Стек проекта:** Next.js (App Router, Server Components), Prisma ORM, Kysely, PostgreSQL, Upstash Redis, Tailwind CSS, Framer Motion.  
> **Результат:** 100% страниц в зеленой зоне Core Web Vitals, средний Lighthouse Performance вырос до **100**, средний LCP сократился с **1821 ms до 413 ms**, 0 медленных страниц из 83.

2. **Авторизация (2 страницы):** Вход, регистрация с выбором тенанта.
3. **Рабочая зона CRM/ERP (46 страниц):** Дашборд, смены, графики, табель учета времени, расчет зарплат, сметы, клиенты, контракты, оборудование, журнал аудита, финансы, отчеты.

## 3. Глубокий разбор реальных причин (Root Cause Analysis)

В процессе профилирования гипотезы «виноват медленный React» или «тяжелый бандл» были опровергнуты. Настоящие причины крылись в архитектуре SSR, сети и каскадных таймерах.

### Причина №1: Сетевой водопад Rate Limiter в Server-Side Rendering
- **Как было устроено:** При каждом обращении к `"use server"`-экшену функция `requireTenant()` вызывала `assertUserActionRateLimit()`.
- **В чем скрывалась ловушка:** Redis был подключен через внешний REST API (Upstash), где каждый сетевой вызов занимал **~215 ms**. На один экшен проверялось 2 ключа (user-wide и per-tenant) последовательно, и каждый делал `TTL` + `INCR` + `EXPIRE` последовательно.
- **Математика задержки:** 1 серверный экшен = 4 последовательных HTTP-запроса = ~860 ms. Дашборд вызывал 5 экшенов:
  $$\text{Задержка} = 5 \text{ actions} \times 4 \text{ хопа} \times 215 \text{ ms} \approx 4300 \text{ ms}$$
  Сервер просто ждал внешнюю сеть Upstash 4 секунды до отдачи первого байта HTML!

### Причина №2: Водопад N+1 в серверном расчете зарплат
- В `/security/salary` расчет выплат выполнялся в цикле:
  ```typescript
  // БЫЛО: 100 последовательных запросов к БД на один рендер страницы!
  for (let i = 0; i < guards.length; i++) {
    await calculateMonthlySalaryAction(guards[i].id);
  }
  ```
- Каждый вызов открывал транзакцию и сканировал табель. Итог: **16.8 секунд рендера страницы**.

### Причина №3: Каскадные таймеры Framer Motion (Убийца TBT)
- На странице зарплат и в списках сотрудников использовалась «красивая» анимация строк:
  ```tsx
  // БЫЛО: каскадный таймер на каждой строке
  <motion.tr transition={{ delay: index * 0.05 }} />
  ```
- На таблице из 100 сотрудников браузер одновременно создавал **100 активных JavaScript-таймеров**. Главный поток процессора зависал на **3.5 секунды (TBT 3516 ms)**.

### Причина №4: `initial={{ opacity: 0 }}` на первом экране (Задержка LCP)
- Заголовки `h1` и баннеры на лендингах были обернуты в анимации с начальной прозрачностью `0`.
- Браузер не мог зафиксировать LCP (Largest Contentful Paint), пока не загрузился весь бандл JS, не произошла гидратация и не закончилась анимация длительностью 500–800 ms.

### Причина №5: Отсутствие кириллического сабсета в веб-шрифте
- Шрифт `Inter` был подключен в Next.js только для `subsets: ["latin"]`.
- Интерфейс на русском языке приводил к тому, что браузер сначала отрисовывал системный fallback (Arial/Times), а затем принудительно перерисовывал все глифы, вызывая скачки текста и CLS.

## 4. Комплекс инженерных решений: 9 блоков оптимизации

### Блок 1: Параллелизация SSR и очистка шрифтов
- Перевод независимых запросов данных в `page.tsx` на `Promise.allSettled`.
- Время генерации HTML `/security` сократилось с **4040 ms до 895 ms** (−3.1 секунды!).
- Удален дублирующий `@import` Google Fonts из CSS. В `next/font` добавлен сабсет `cyrillic`.
- Снята начальная прозрачность `opacity: 0` у заголовков выше сгиба экрана.

### Блок 2 и 3: Оптимизация сетевого взаимодействия с Redis
- 3 последовательных вызова к Redis (`TTL`, `INCR`, `EXPIRE`) свернуты в **один атомарный Lua-скрипт (`EVAL`)**.
- Проверка пользовательского и тенантного ключей объединена в `Promise.all`.
- 4 сетевых хопа превратились в **1**. LCP страницы `/security/shifts` упал с **3860 ms до 508 ms**.

### Блок 4 и 5: Архитектурное разделение Rate Limiter (Read vs Write)
- **SSR Чтения (`mode: "read"`):** Во время серверного рендеринга обращение к внешнему Redis исключено на 100% (**0 ms оверхеда**).
- **Мутации (`mode: "write"`):** Все 226 мутаций защищены строгим лимитом 60 запросов/мин.
- **Защита от спуфинга:** Внутренний reverse-proxy формирует заголовок `x-action-rpc`, который принудительно срезается с внешних клиентских запросов.
- **Результат:** 0 ms задержки на рендеринге во всех трех вертикалях (Security, Beauty, Yacht).

### Блок 6: Пакетные запросы и динамическая загрузка (Dynamic Imports)
- **Ликвидация N+1 в зарплатах:** Создан метод `getMonthlySalariesBatchAction` с предзагрузкой данных через `findManyByPeriod` и SARGable-диапазон дат `WHERE date >= :start AND date < :end`. Время рендера упало с 16.8 с до **869 ms** (в 19 раз быстрее!).
- **Финансы:** Тяжелая библиотека графиков `recharts` (~200 KB) вынесена в `next/dynamic` с отложенной загрузкой на клиенте.
- **Ликвидация спиннеров:** Формы редактирования переведены на Server Component с прелоадом данных. Вместо пустого спиннера `<Loader2 />` клиент получает готовый HTML в первом пакете.

### Блок 7: Перенос публичных страниц на Pure Static Site Generation (SSG)
- Все 35 публичных страниц лендингов и маркетинга переведены на `export const dynamic = "force-static"`.
- Публичные страницы отдаются с диска за **5–20 ms** без обращений к базе данных.
- Фоновые вращения `HeroBg` перенесены с Framer Motion на аппаратный CSS GPU Compositor (`transform: rotate`, `will-change: transform`).

### Блок 8: Устранение Layout Shift (CLS = 0.0000)
- На странице смет `/security/estimates/[id]/edit` зафиксирована минимальная высота блока итогов (`min-h-[108px]`).
- Скелетон загрузки строго выровнен по 2-колоночной сетке формы.
- CLS снижен с **0.2152 до 0.0000**.

## 6. Золотые правила для любых веб-проектов

1. **Никакой внешней сети во время SSR-рендеринга:** Rate-лимитеры, аналитика и проверки должны быть отделены от рендеринга страниц.
2. **Параллелизация вместо каскадов:** Если компонент читает 3 таблицы — используйте `Promise.allSettled`, а не 3 последовательных `await`.
3. **Убирайте `opacity: 0` выше сгиба экрана:** LCP-контент должен быть виден мгновенно в сыром HTML до запуска JS.
4. **Не используйте JS-таймеры для списков:** Заменяйте каскадные анимации строк таблицы на статический рендер или CSS-анимации.
5. **Резервируйте высоту динамических блоков:** Любой блок, подгружающий данные после монтирования, обязан иметь фиксированный `min-height` или скелетон равного размера для CLS = 0.
